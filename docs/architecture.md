# 基础架构说明

## 设计目标

项目只搭建鉴权、实时通信、支付和系统防护四个模块的边界。业务模块之间不直接依赖彼此的实现，跨模块协作通过接口契约或 Kafka 事件完成。

## 产品定位

平台包含三条责任边界不同的业务线：

```text
官方自营：平台入库激活码 → 官方商品上架 → 买家支付 → 平台交付
用户寄售：卖家托管激活码 → 平台校验并保管 → 买家支付 → 平台交付 → 卖家结算
道具撮合：用户发布道具信息 → 买卖双方在交流窗口沟通 → 双方自行交易
```

前两类属于平台内交易，共用支付、码库存和交付能力，但库存所有方及结算规则不同。激活码属于敏感数字资产，未来实现必须保证密文存储、明文最小暴露、单码只交付一次，以及支付、库存和交付状态之间的幂等一致性。

第三类是信息撮合，不进入平台支付链路。平台只负责信息发布、会话建立和必要的内容治理，不保管道具、不代收交易款、不提供交易担保，也不承担履约责任。当前提交只记录这些领域约束，不实现对应业务模块。

## 依赖方向

```text
进程入口
  └─ 组合根
      ├─ HTTP 交付层 → 应用服务 → 领域接口 ← 基础设施适配器
      └─ Kafka 消费者 → 实时通信服务 → WebSocket 连接中心

支付模块 ──发布 payment.lifecycle.v1──> Kafka ──消费──> 实时通信模块
系统防护模块 ──作为中间件或外部调用包装器作用于边界
```

约束如下：

- 支付模块不直接调用 WebSocket。
- 实时通信模块不读取支付数据表。
- 系统防护模块不访问业务仓储。
- 鉴权模块只负责身份、令牌和会话，不管理支付或连接。
- 跨模块事件统一使用带版本的事件信封。

## 模块边界

### 鉴权

当前只实现访问令牌校验与身份上下文，登录、刷新会话和权限模型保留为下一阶段扩展点，避免在骨架期虚构用户业务。

### 实时通信

当前实现鉴权握手、连接登记、断开清理和按用户推送的连接中心。后续可承载激活码订单状态通知，以及软件激活码买卖双方的商品咨询窗口；聊天记录、内容审核和离线消息暂不实现。

### 支付

当前只实现创建支付意图的边界；支付渠道使用本地替身，创建后发布支付生命周期事件。支付能力服务官方自营和用户软件激活码寄售。持久化、回调与幂等状态机留到业务阶段。

### 系统防护

提供限流、并发隔离和熔断的最小实现及中间件挂载点，具体分布式策略可通过接口替换。

## 最小接口

```text
GET    /healthz
GET    /readyz
GET    /api/v1/me
GET    /api/v1/realtime/ws
POST   /api/v1/payments
```

## 当前阶段不做

- 真实支付渠道接入、退款、订单和账务。
- 多实例 WebSocket 路由和离线消息补偿。
- 完整的权限管理后台。
- 官方自营、用户寄售、道具信息、交流会话、激活码库存、订单交付、资金结算、营销和搜索等业务。
- 复杂监控面板及生产级服务治理平台。

这些能力只保留清晰扩展点，避免基础架构提前膨胀。
